Method

How each number is produced (and how to check it)

1 · Fixture discovery

The HotSpawn Pick'ems lobby is a client-rendered page that calls the public fixtures API phpstack…/api/v1/fixtures. This build uses both: the lobby page for the rendered pick cards and the API for kick-off, lock time and status. Every fixture keeps its HotSpawn id and, where HotSpawn publishes one, its match permalink. HotSpawn's crowd-pick percentages are not parsed anywhere in this pipeline.

2 · Prices → probabilities

For each book with a two-sided price: implied = 1/decimal, then normalise the pair to 100% (p = implied_a / (implied_a + implied_b)). The overround is published next to the price so you can see the book's margin. When several books price the same fixture the no-vig probabilities are averaged; the spread between books is shown on the row.

Quote joins are evidence-gated: a quote is used only when the kick-off agrees within 90 minutes and the pairing is either an exact name match, a documented alias with the roster/kick-off evidence on Sources, or a publisher-ordered quote already attached to that fixture id. Everything that fails those gates is dropped, not coerced.

3 · Originated lines (no book prices the match)

p = 1 / (1 + exp(-k · C · (points_a - points_b)))

  • C = 0.0056000078 — Valve's own rating slope, from model/fit.js.
  • k = 0.43077894236569164 — this project's fitted market-vs-rating scale factor.
  • points — the official Valve VRS points for each side, from standings_global_2026_10_05.md.

4 · Duplicate Valve rows

When Valve's standings list the same organisation more than once (one row per counted roster), select the row whose roster lists a full five and whose latest published match date is the most recent; break ties on higher points. Alternatives are published on the Flagged for review page.

Three fixtures on today's board hit this rule (Banda Chuya, The Huns, benched gods). Every alternative row Valve publishes for those teams is kept in the board data next to the chosen one, and the pick is flagged vrs duplicate rows resolved by published rule.

5 · Bounds instead of point estimates

If one side has no row in Valve's published table, that side is at or below the published floor (#380, 381 pts). The listed side's number is published as a lower bound and the unlisted side's number as an upper bound. It is never presented as a point estimate.

6 · Verification in this repository

  • python3 scripts/5f903db4/build.py re-derives every probability from the raw decimals and Valve points stored in data/5f903db4/board.json.
  • python3 -m unittest tests.test_5f903db4 -v re-computes the no-vig prices and the originated lines from the raw inputs, asserts that every row has a pick and two probabilities, that every row carries at least one https source, that the bounds are marked, and that no HotSpawn crowd percentage appears anywhere in the published pages.
  • The workflow .github/workflows/everypick-5f903db4.yml re-runs collection, build and tests every four hours and only commits when the tests pass.
