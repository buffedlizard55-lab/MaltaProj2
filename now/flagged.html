IR-1 - Settled history in data/fe803b80/board.json cannot be used as a track record

The published track_record claims 99.5% accuracy for model-only picks (366 won / 2 lost) and 98.4% for market-only picks (121 / 2), while blended picks sit at 70.2%. Picks whose own published probability averages 0.667 cannot hit 99.5% of the time. Two mechanical causes are visible in the file: 'history' holds 4,870 rows for only 107 unique fixtures (the same fixture is re-recorded at every ~26-minute refresh, so samples are 20-200x inflated), and every 'settled: won' row has pick == winner by construction, which means the pick string is being re-derived from the result rather than from the published line. Anyone quoting 'our model hits 99%' from this file would be publishing a false claim.

Links: buffedlizard55-lab/MaltaProj2 buffedlizard55-lab/MaltaProj2

What we did: Not edited (file is another session's scope). Reported here and in COORDINATION.md; the day-5 desk republishes its own numbers from raw reads instead.

IR-2 - Duplicate Valve VRS rows silently mis-joined

Valve's 2026_10_05 global file lists 'chinggis_warriors' twice (ranks 87 and 220) and 'betclic' twice (45 and 183) because retired lineups keep their rows. The board's vrs_ambiguous_keys contains only 'club333:americas:Club 333', and scripts/fe803b80/core.py has no ambiguity guard, so 1081863 was joined to a 685-point row when the active lineup holds 1084 points, and 1081546 could have been joined to the disbanded 765-point Betclic row. Both joins are corrected in this session's override file with the lineup evidence.

Links: ValveSoftware/counter-strike_regional_standings buffedlizard55-lab/MaltaProj2

What we did: Fix request logged for the board owner: refuse any rating join where the same team name matches more than one row unless the lineup also matches.

IR-4 - Rendered clocks are viewer-local on HLTV, the HotSpawn lobby and bo3.gg

Three independent traps in one hour: HLTV served the grand final as '11:00' to this session (a UTC-4 proxy) while its own search-indexed copy and Liquipedia show 17:00 CEST; the HotSpawn lobby rendered 'Oct 18, 04:00' next to a 'Locks in 07:06:12' countdown that only makes sense for an 08:00Z fixture; bo3.gg printed 'Oct 20, 03:00' for a fixture whose API epoch is 07:00Z. Any pick locked on a read of the printed clock would have been three to four hours late.

Links: matches/2399417 counterstrike/Thunderpick lobby

What we did: Every time on this desk is UTC, decoded from HotSpawn's API epoch milliseconds; the rendered strings are only kept in the read ledger (R2, R11) as a consistency check on that decode.

The generator called the Aurora-Falcons third-place match 'the grand final' on two separate pages and credited Falcons with a 'two-match winning streak' the morning after they lost 1-2 to BETBOOM. Its FURIA '80% H2H winrate' line is a record count, not a probability.

Links: matches/aurora-gaming-vs-falcons-esports-18-10-2026 matches/furia-vs-betboom-team-18-10-2026
